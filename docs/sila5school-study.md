## 0. สรุปสั้น

1. **ที่นำแนวคิดมาใช้ได้:** แกนหลักครบทั้ง loop คือ Canvas → AI สังเคราะห์แผน → แผนลงมือทำ → บันทึกรายสัปดาห์ → timeline รายเด็ก ซึ่งตรงกับ Product Loop ข้อ 48 เกือบทั้งหมด
2. **loop นี้เพิ่งเปิดใช้ในปีการศึกษา 2569 และยิ่งขั้นหลังยิ่งมีคนใช้น้อย:** โรงเรียน 818 → เขียน Canvas 91 → ใช้ AI 51 → เปิดใช้แผนลงมือทำ 2 → มีบันทึกรายสัปดาห์ 2 โรงเรียน ข้อมูลจริงของขั้นลงมือทำและหลักฐานจึงยังไม่พอใช้สรุปพฤติกรรมครู (หัวข้อ 1.1)
3. **ที่ระบบเดิมไม่มีเลย** ต้องสร้างใหม่: Coaching, Subscription/Seat/Entitlement, Payment, Course แบบมีบทเรียนและวิดีโอ, การเตือนตามแผนลงมือทำที่ส่งจริง
4. **ระบบเดิมผูกทุกอย่างกับคู่ (โครงการ = ปีการศึกษา, โรงเรียน):** ครูหนึ่งคนอยู่ได้ 1 โรงเรียนต่อปี SkillWise ต้องแยก Identity / Membership / Seat ออกจากกัน (ข้อ 33, 34)
   - ข้อมูลจริง: แทบไม่มีครูอยู่ 2 โรงเรียนพร้อมกัน แต่มีครูกลับมาข้ามปี 425 คน และ 79% ของโรงเรียนในปี 2569 มีครูคนเดียว
5. **งานสำคัญหลายส่วนอยู่นอก repo:** ให้คะแนน Canvas, อนุมัติ, ตั้งสถานะผ่านอบรม, ส่งแจ้งเตือน email/LINE และจัดการเนื้อหาหน้าเว็บ SkillWise ต้องทำให้จบในระบบเดียว (ข้อ 60.10.4)
6. **LINE:** repo นี้ทำได้แค่ผูกบัญชี (ผูกแล้ว 12% ของบัญชี) ส่วนหลังบ้านกลางส่ง LINE จริงราว 1,700 ข้อความในช่วง มี.ค.–ก.ค. 2026 แต่เป็นคำเชิญและเตือนก่อนอบรมเท่านั้น ยังไม่มีการเตือนตามแผนลงมือทำและไม่รับข้อความจากครู งานในข้อ 60.10.6 จึงยังต้องสร้างใหม่
7. **พบปัญหาข้อมูลส่วนบุคคลของนักเรียนและช่องโหว่หลายจุด** (หัวข้อ 6) รวมถึงตารางสำรองที่มีข้อมูลส่วนบุคคลค้างอยู่ในฐานจริง SkillWise ต้องออกแบบกันไว้ตั้งแต่แรก
8. ข้อสังเกตจากข้อมูลจริงที่กระทบการออกแบบอยู่ในหัวข้อ 7.1 · ร่างฟีเจอร์ Phase 1 อยู่ในหัวข้อ 8 และคำถามที่ทีมต้องตัดสินอยู่ในหัวข้อ 9

## 2. ผู้ใช้ บทบาท และองค์กร

### 2.1 Login และตัวตน

- **Login:** ใช้ Google อย่างเดียว (`module/user/controller/loginController.php:94-276`) login ครั้งแรกระบบสร้าง `person` + `user` แต่ถ้ามี `person` จากคำเชิญที่อีเมลตรงกัน จะใช้ `person` นั้นแทน (`loginController.php:186-189`)
- **Remember token:** อายุ 7 วัน เก็บเป็น SHA256 ผูกกับ fingerprint ของ browser+OS (`library/rgt/siteAuth.php:19-143`)
  - หมุน token เฉพาะตอนใช้ทำ auto-login (ไม่มี session หรือ session หมดอายุ) และไม่หมุนในช่วง grace 60 วินาที (`siteAuth.php:21-30, 77-81`)
  - หมุนแต่ละครั้งได้อายุใหม่ 7 วัน จึง**ไม่มีอายุสูงสุด** · timeout 30 นาทีแทบไม่มีผลเมื่อมี remember token
- **Session:** หมดเมื่อไม่ใช้งาน 30 นาที
- **LINE:** ใช้**ผูกบัญชีเพื่อรับแจ้งเตือน**เท่านั้น login ด้วย LINE ไม่ได้ (`module/line/controller/liffController.php:50-198`)
  - ข้อมูลจริง: ผูกแล้ว 502 จาก 4,098 บัญชี (12%)
- **Consent:** เก็บค่าความยินยอมด้าน privacy และโฆษณา พร้อมเวลา ไว้ในตาราง `user`
  - ข้อมูลจริง: สองค่านี้เท่ากันทุกบัญชี (ยอมรับทั้งคู่ 3,588 / ไม่ได้ยอมรับทั้งคู่ 510) ไม่มีใครเลือกแยก
- **โรงเรียนและตำแหน่งเก็บไว้ที่ตัวคน:** `person` มี `person_type_id` (ตำแหน่ง) และ `person_school_id` (โรงเรียน) **ได้อย่างละค่าเดียว**
  - ข้อมูลจริง: `person` 4,099 คน เป็นครู 1,549 / ผอ. 136 / รองผอ. 43 / นักเรียน 526 / บุคคลทั่วไป 1,821
- **Login-as:** แอดมินเข้าระบบนี้ด้วยลิงก์ HMAC อายุ 5 นาที (`loginController.php:278-313`)

### 2.2 บทบาท

ระบบฝั่งครู**ไม่ได้ใช้ RBAC** สิทธิ์มาจากประเภทครูในโครงการ (`school_training_kru.stk_type_id`)

| type | บทบาท | ทำอะไรได้ |
|---|---|---|
| 1 | ผู้ประสานงานหลัก (คนแรกที่สมัครโรงเรียนเข้าโครงการ) | ทุกอย่าง รวมถึงใช้ AI สรุปแผน, จัดแผนลงมือทำ, บริหารทีม, แชร์รายงาน |
| 2 | ครูผู้ช่วย | สร้าง Canvas, บันทึกงานที่มีชื่อตัวเอง, เขียนเรื่องราว |
| 3 | ครูร่วมกิจกรรม | อ่านอย่างเดียว ผ่าน whitelist ของ action แบบ default-deny (`library/module/console.php:106-141`) |

- ครูเห็นนักเรียนเฉพาะห้องที่ตัวเองดูแล (`stk_class`) (`console.php:527-543`)
  - ยกเว้นเมนู 6 และ 7 ที่โหลดนักเรียนทั้งโรงเรียนให้ครูทุก type รวมถึง type 3 (`library/module/report.php:55-62`, `console.php:116`)
- ระดับสิทธิ์แบบตัวเลข (1 ดู / 2 เพิ่ม / 3 แก้ / 5 ทั้งหมด) และตาราง `role` / `resource` / `rrp` ใช้ในระบบแอดมินเท่านั้น
- ในแอปไม่มีวิธีโอนตำแหน่งผู้ประสานงานหลัก

### 2.3 องค์กรและการสมัครโครงการ

- **Master data โรงเรียน:** `school` + สังกัด (`school_department` → `school_ministry`) + เขตพื้นที่ + ที่อยู่แบบลำดับชั้น lv1–lv5
- **โครงการ = ปีการศึกษา:** ตาราง `project` เก็บโควตาโรงเรียน, ช่วงสมัคร, ช่วงแจ้งรับสื่อ และช่วงดำเนินงาน
- **โรงเรียนสมัครเข้าโครงการ** (`module/project/controller/registerController.php`):
  1. เลือกโรงเรียน
  2. กรอกข้อมูลตัวเอง ข้อมูลโรงเรียน และข้อมูล ผอ.
  3. เลือกระดับภารกิจ M1–M3, ห้องเรียน และรอบปฐมนิเทศ
  4. ยืนยัน OTP ทาง SMS
  5. บันทึก: ถ้าโควตาเต็มได้สถานะ "สำรอง" ถ้าไม่เต็มได้ "สมัคร" (`:1023-1048`)
  - ลำดับสถานะ: 1 สำรอง → 2 สมัคร → 3 เข้าร่วม → 4 ผ่าน (แอดมินเป็นคนเลื่อน)
  - ระดับ M1–M3 คำนวณจากจำนวนดาวของปีที่แล้วและสองปีก่อน (`:623-659`, `library/module/global.php:2320-2335`) · server ไม่ตรวจว่าระดับที่ส่งมาอยู่ในชุดที่อนุญาต (`registerController.php:829, 862`)

### 6.3 Tech debt ที่ SkillWise ต้องไม่ทำซ้ำ

- เก็บ id หลายค่าเป็น CSV ใน varchar (`stk_class`, `sat_stc_ids`, `sap_assistant_ids`)
- flag สถานะของหลายเมนูกองอยู่บนแถวเดียว (`school_training`)
- เลือก context ของครูด้วย `LIMIT 1` โดยไม่มี ORDER BY ผลจึงไม่แน่นอนเมื่อครูอยู่หลายโรงเรียนหรือหลายโครงการ
- AI เขียนทับข้อมูลโดยไม่มี version · ความสัมพันธ์สำคัญไม่มี FK (Canvas ↔ แผน)
- ผูกข้อมูลด้วยการค้นข้อความ (นักเรียนใน Canvas, สัญญาณความสำเร็จ)
- โควตาและสต็อกไม่ใช้ transaction ทำให้เกิด race condition ได้
- ความหมายของ status ใน schema ไม่ตรงกับโค้ด (`activity_status_id`, `round_status_id`)
- งานหลักกระจายอยู่หลายระบบ (แอดมิน, ระบบให้คะแนน, คิวแจ้งเตือน, Notion)
- hard-code ของเฉพาะโครงการ: 7 กิจวัตร, M1–M3, ดาว, เกณฑ์สมุด 360/600, ชั้น ป.4 ขึ้นไป, id ของ activity_type, ตารางค่าส่ง
- ไฟล์ schema ใน repo ตามฐานจริงไม่ทัน (ขาด 13 ตาราง) และมีตารางสำรอง ตารางพัก และตารางเก่าค้างในฐานจริง 17 ตาราง โดยไม่มีกำหนดลบ
- ความยินยอม 2 ค่าที่ไม่ได้แยกกันจริง และคอลัมน์ที่มีช่องในฟอร์มแต่ค่าไม่ถูกบันทึก (`sc_target` หัวข้อ 3.1)
- remember token ที่ต่ออายุได้ไม่สิ้นสุด และ link token ที่เก็บค่าจริงไม่ hash (หัวข้อ 2.1, 5.1)
- กฎสำคัญบางข้อบังคับแค่ฝั่งหน้าเว็บ เช่น วันจันทร์–ศุกร์ของกิจวัตร และความยาว 800 ตัวอักษรของ Canvas

### 7.1 ข้อสังเกตจากข้อมูลจริงที่กระทบการออกแบบ

ทุกข้อเป็นข้อเสนอให้ทีมพิจารณา ไม่ใช่ข้อสรุป

1. **ครูทำงานคนเดียวเป็นเรื่องปกติ:** 79% ของโรงเรียนมีครูคนเดียว flow ของครูจึงต้องใช้ได้ครบโดยไม่ต้องมีทีม (ข้อ 33)
2. **ตัวตนที่ต่อเนื่องข้ามรอบสำคัญกว่าการอยู่หลายองค์กรพร้อมกัน:** ครูกลับมาข้ามปี 425 คน แต่อยู่ 2 โรงเรียนพร้อมกันแค่ 1 กรณี ระบบยังควรรองรับหลายองค์กรตามข้อ 33 แต่ประวัติของครูข้ามรอบต้องไม่หาย
3. **งาน AI ต้องรับมือความล้มเหลวได้:** งานสังเคราะห์แผนล้มเหลว 30% `AIJob` จึงต้องมี retry แจ้ง error ให้ครูเข้าใจ และไม่หักเครดิตเมื่อล้มเหลว (ข้อ 60.10.4)
4. **feedback ต่อ Canvas ถูกใช้จริง:** 57% ของ Canvas ถูกแก้หลังได้คะแนน ควรเก็บ version ของทั้ง Canvas และ feedback เพื่อให้เห็นพัฒนาการ (ข้อ 12)
5. **ขั้นลงมือทำและหลักฐานยังไม่มีข้อมูลพอ:** มีแค่ 2 โรงเรียนที่ใช้จริง ไม่ควรใช้ระบบเดิมเป็นหลักฐานว่า flow นี้ใช้ได้ ควรทดสอบกับครูจริงก่อน lock design
6. **ไม่ควรบังคับให้มีรายชื่อนักเรียนก่อนเริ่มใช้:** มีแค่ 21% ของโรงเรียนที่บันทึกนักเรียน ฟีเจอร์ที่ผูกกับนักเรียน (CanvasTarget, timeline) ควรเริ่มใช้ได้โดยไม่ต้อง import นักเรียนครบ
7. **LINE น่าจะได้ผลกว่า email:** อัตราคลิกของ LINE 17% เทียบกับ email 3% สนับสนุนแนวทาง LINE ในข้อ 60.10.6 (ข้อความส่วนใหญ่เป็นคำเชิญ จึงยังเทียบกับการเตือนตามแผนโดยตรงไม่ได้)
8. **การตรวจแผนเป็นคอขวด:** ยังไม่มีแผนไหนผ่าน มีรอตรวจ 46 และไม่ผ่าน 31 เกี่ยวกับคำถามในหัวข้อ 9 ข้อ 2 ว่าจะยังมีการตรวจผ่าน/ไม่ผ่านหรือใช้ Coach Feedback แทน
9. **การย้ายข้อมูลต้องมีแผนลบ:** ระบบเดิมมีตารางสำรองที่มีข้อมูลส่วนบุคคลค้างอยู่ 17 ตาราง SkillWise ควรกำหนดตั้งแต่แรกว่าข้อมูลที่ import หรือสำรองไว้จะถูกลบเมื่อไหร่ และใครรับผิดชอบ

## 9. คำถามที่ทีมต้องตัดสิน

**กระทบ Phase 1 โดยตรง**

1. คะแนน AI ของ Canvas เป็นเงื่อนไขบังคับก่อนทำแผน หรือเป็นแค่ feedback (ข้อ 12) ถ้าใช้เป็นเงื่อนไข จะยังใช้น้ำหนักคะแนนเดิม 2/1.5/1/1.5/1.5/1.5/1 หรือไม่
2. แผนพัฒนายังต้องมีการตรวจ "ผ่าน/ไม่ผ่าน" หรือใช้ Coach Feedback แทนทั้งหมด
3. Canvas pool ให้ทั้งองค์กรเห็นเป็นค่าเริ่มต้น หรือเป็นของส่วนตัวแล้วให้ครูแชร์เอง (ข้อ 31)
4. อนุญาตให้บันทึกย้อนหลังหรือไม่ และย้อนได้กี่สัปดาห์
5. Coaching ใน Phase 1 เป็นรูปแบบไหน (1:1, กลุ่ม, คลินิกรายเดือน) และใครเป็นโค้ช
6. Phase 1 รับเงินผ่าน gateway เลย หรือเริ่มจากโอนเงิน/ใบแจ้งหนี้แล้วให้แอดมินยืนยัน
7. "รอบการพัฒนา" ของครูผูกกับปีการศึกษา หรือกับรอบ subscription
8. ครูหนึ่งคนสังกัดหลายองค์กรพร้อมกันได้หรือไม่ และคนที่ซื้อ seat กับผู้ประสานงานเป็นบทบาทเดียวกันหรือไม่

**ข้อมูลที่ยังขาด**

9. ขอเข้าถึง repo `sila5-admin`, หลังบ้านกลางของ RGT และระบบ "rgt" ที่ให้คะแนน Canvas ได้หรือไม่ ต้องใช้ดู rubric ฉบับเต็ม ขั้นตอนอนุมัติ และคิวแจ้งเตือน
10. ปัญหาในหัวข้อ 6 ของระบบเดิม (รวมถึงตารางสำรองที่มีข้อมูลส่วนบุคคล) จะแจ้งทีม Sila5School ผ่านช่องทางไหน

**เพิ่มจากการดูฐานข้อมูลจริง**

11. SkillWise จะย้ายข้อมูลจาก Sila5School มาหรือไม่ (บัญชีครู, Canvas, เรื่องราว, ประวัติอบรม) ถ้าย้าย ต้องกำหนดขอบเขต การขอความยินยอม และวิธีจัดการข้อมูลนักเรียนก่อน (ข้อ 31, 60.2)
